# Exercício 3.1 — Structured Output e Verificações Determinísticas

**Papel:** Desenvolvedor · **Tópico:** Harness Engineering
**Artefatos entregues:** `src/services/response-validator.ts`, `src/shared/logger.ts`, `tests/unit/response-validator.test.ts`

---

## 1. Schema Zod do structured output

```ts
export const structuredResponseSchema = z.object({
  answer: z.string().min(1, "answer não pode ser vazio"),
  source_document: z.string().min(1, "source_document não pode ser vazio"),
  confidence_score: z.number().min(0).max(1),
}).strict();
```

Decisões relevantes:
- `.strict()` — rejeita campos extras em vez de ignorá-los silenciosamente.
- `min(1)` em `answer` e `source_document` — string vazia passaria em `z.string()` puro, o que reabriria exatamente o buraco que o guardrail 1 deveria fechar.
- `confidence_score` limitado a `[0, 1]` — sem isso o campo existe mas não tem significado (ex: `confidence_score: 42`).

## 2. `response-validator.ts` — schema + 2 guardrails

Implementado em [`src/services/response-validator.ts`](../../src/services/response-validator.ts). Resumo do fluxo:

1. `structuredResponseSchema.safeParse(raw)` — se falhar, loga os `issues` do Zod (nível `warn`, via pino) e retorna `SAFE_FALLBACK_RESPONSE`.
2. Guardrail "carga perigosa + devolução" (POL-001, seção 3.2) — se a resposta menciona os dois temas sem uma negativa explícita, bloqueia e loga o motivo.
3. Toda falha retorna a mesma resposta padrão seguraSAFE_FALLBACK_RESPONSE — nunca deixa a resposta original vazar.

Isso implementa os dois guardrails do enunciado:
- **Guardrail 1** (`source_document` obrigatório) — coberto pelo schema (`min(1)` + `.strict()`), não por uma checagem separada, já que "campo ausente" e "campo vazio" são a mesma classe de falha de formato.
- **Guardrail 2** (carga perigosa + devolução) — função dedicada `violatesDangerousCargoGuardrail`.

## 3. Code review (Claude) sobre a primeira versão

Uma primeira implementação "gerada pelo Copilot" (simulada, com base no que o enunciado descreve como problemas típicos desse tipo de guardrail) tinha esta forma:

```ts
// v1 — versão revisada
export const structuredResponseSchema = z.object({
  answer: z.string(),
  source_document: z.string(),
  confidence_score: z.number(),
});

export function validateResponse(raw: unknown) {
  const parsed = structuredResponseSchema.safeParse(raw);
  if (!parsed.success) {
    console.log("validação falhou", parsed.error);
    return { ok: false, response: SAFE_FALLBACK_RESPONSE };
  }

  const { answer } = parsed.data;
  if (answer.includes("carga perigosa") && answer.includes("devolução")) {
    console.log("guardrail de carga perigosa acionado");
    return { ok: false, response: SAFE_FALLBACK_RESPONSE };
  }

  return { ok: true, response: parsed.data };
}
```

**Problemas identificados e correções aplicadas:**

| # | Problema | Por que é um problema real | Correção |
|---|---|---|---|
| 1 | Schema sem `.strict()` e sem `min(1)` nas strings | `z.object()` puro permite campos extras (um `sources` alucinado passaria despercebido) e aceita `source_document: ""` — o guardrail 1 do enunciado ("se não tiver, a resposta é rejeitada") não cobre o caso de vir vazio, só o caso de vir ausente | Adicionado `.strict()` no schema e `min(1)` em `answer`/`source_document`; `confidence_score` limitado a `[0,1]` |
| 2 | Regex/`includes` literal para "carga perigosa" + "devolução" | `answer.includes("carga perigosa")` não bate com "cargas perigosas", "Carga Perigosa" (maiúsculas) nem com "devolvida"/"devolver" — a POL-001 usa "cargas perigosas" no plural na seção 3.2, então a v1 nunca dispararia no caso real de uso | Trocado por regex (`/carga[s]?\s+perigosa[s]?/i`, `/devolu[cç][aã]o\|devolv.../i`) cobrindo singular/plural, variações de conjugação e case-insensitive |
| 3 (bônus) | O guardrail 2 bloqueava qualquer menção conjunta aos dois temas, inclusive quando a resposta já continha a negativa correta (ex: "cargas perigosas **não** são elegíveis para devolução") | Isso tornaria o assistente incapaz de responder corretamente à pergunta mais comum sobre o tema — falso positivo em massa, não só uma falha de guardrail | Adicionado `EXPLICIT_DENIAL_PATTERN` — só bloqueia quando os dois temas aparecem **sem** uma negativa explícita ("não", "vedado", "impossível") por perto |
| 4 (bônus) | `console.log` para registrar falhas | Viola a convenção do projeto (AGENTS.md: "pino para logging, nunca console.log") e não permite níveis/estrutura de log em produção | Criado `src/shared/logger.ts` (pino) e trocado por `logger.warn({...}, mensagem)` |

## 4. Distinção prompt (probabilístico) vs. código (determinístico)

- O **prompt** (`prompts/system-prompt.md`) instrui o modelo a sempre citar a fonte e a negar devolução de carga perigosa — isso reduz a frequência do problema, mas não garante nada: é um pedido, não uma restrição.
- O **`response-validator.ts`** é a garantia: roda depois da geração, não confia no que o modelo disse que fez, e qualquer resposta que viole o contrato (formato ou regra de negócio) é substituída por `SAFE_FALLBACK_RESPONSE` antes de chegar ao atendente ou ao bot do Teams. Isso é o harness — o prompt tenta acertar, o código impede que o erro se propague quando o prompt falha.

## 5. Testes

`tests/unit/response-validator.test.ts` — 9 testes, todos passando (`npx vitest run tests/unit/response-validator.test.ts`):
- Schema: resposta válida, `source_document` ausente, `source_document` vazio, `confidence_score` fora de `[0,1]`, campo extra não previsto.
- Guardrail POL-001 3.2: negativa correta passa, afirmação de devolução é bloqueada, variações de singular/plural/conjugação são bloqueadas, respostas que não tocam no tema passam normalmente.
